## 设计阶段（M0 之前发生，M0 补录）

### [设计-1] AI 断言「企业微信强制要求公网回调 URL」，导致平台错选成钉钉

- **我给 AI 的原始 prompt**：「我要做一个公司内部 AI 助手，IM 入口要求不暴露公网、
  本地笔记本就能演示。帮我选一个 IM 平台和接入方式。」
- **AI 给的方案**：直接排除企业微信，理由是「企业微信接收消息**必须**配置公网 HTTPS
  回调 URL，还要 ICP 备案和 Token/EncodingAESKey 校验」，转而推荐**钉钉 Stream 模式**
  （出向长连接、免公网）。论证过程看起来非常完整，还列了对比表。
- **我发现的问题**：它说的「必须公网回调」只对**自建应用**这条接入路径成立。我去翻
  企业微信开发者文档的**导航结构**（不是正文），发现「智能机器人」是一条**独立产品线**，
  其下明确有「智能机器人长连接」一节，网关是 `wss://openws.work.weixin.qq.com`——
  **出向 WebSocket，和钉钉 Stream 完全同构，同样免公网**。AI 把「最常见那条路的限制」
  当成了「整个平台的限制」。
- **我的修正**：平台改回企业微信（TDD §1.5 / ADR-02 / ADR-17），钉钉完全移出范围。
  而且这次改判**顺带捡到一个好处**：企业微信智能机器人有 `reply_stream` 原生流式接口，
  而钉钉普通消息**不可编辑**——原本因为「消息发出去就改不了」被迫设计成
  「占位消息 + 追加两条」的降级方案（R10 / ADR-13），现在可以在**同一条消息内做打字机
  原地刷新**。流式输出从 P2 加分项（FR-4-14）直接升为 M9 主线能力。
- **结论**：**AI 对平台能力的判断，默认基于「最常见的那条接入路径」，会把局部限制当成
  全局结论。** 涉及平台选型这种事，必须自己去翻文档的导航结构，先确认「到底有几条路」，
  再问「每条路的约束是什么」。另外这次也提醒我：**否决一个方案前，先确认自己否决的是
  哪一条具体路径**——「企业微信不行」和「企业微信自建应用不行」是完全不同的两句话。

### [设计-2] AI 检索到的 Python SDK 是内容农场仓库，差点被当成可用依赖引进来

- **我给 AI 的原始 prompt**：「找一个企业微信智能机器人长连接的 Python SDK。」
- **AI 给的方案**：推荐 `aibot-python-sdk`，描述写得极其专业——「async WebSocket、
  automatic reconnection、multiple message types、full type hints」，看起来完全对口。
- **我发现的问题**：我去核了一下仓库本体，全是空壳信号：
  - README **只有 18 字节**（就一行标题，所谓「full type hints」无处可查）
  - GitHub API 返回的 `language` 是 **`null`**（说明几乎没有可识别的代码）
  - **无 license**（引入即法律风险，且商业项目不可用）
  - topics 里混着 `whatsapp-automation`、`tensorflow`、`baileys` 等**完全无关**的标签
    —— 这是典型的批量生成仓库刷曝光的手法
- **我的修正**：排除该仓库，改用 `wecom-aibot-sdk-python`（**MIT** license、已上 PyPI、
  README 约一万字有实质内容）。筛选标准固定成四条交叉核对：
  **star 数 / license / README 是否有实质内容 / 最近 push 时间**。
  并在 TDD R18 里把「依赖社区 SDK 而非官方」登记为风险，对策是
  **所有 SDK 调用收敛到 `app/im/wecom.py` 一个文件**，其余模块只依赖 `IMAdapter` Protocol——
  万一这个 SDK 也有问题，替换面被压到最小。
- **结论**：**AI 检索依赖时看的是「描述」，而描述是作者自己写的、可以随便编。**
  选依赖必须自己去看仓库本体的客观信号。一个 18 字节 README + 无 license 的包混进项目，
  等于给代码库加了一个**不可审计**的黑盒——而且它还是 IM 这条 15 分 + 淘汰项链路上的依赖。

## M0 · 仓库骨架与工程基线

### [M0-1] AI 写出来的 `.sh` 脚本全是 CRLF，在 Git Bash 里「看起来能跑」

- **背景 / 我的指令**：按 DEV_PLAN M0 的任务清单，让 AI 写 `scripts/` 下 8 个脚本
  （`check_limits.sh` 要完整实现，其余 7 个只出骨架）。
- **AI 给的方案**：8 个脚本都写出来了，`check_limits.sh` 逻辑也正确——我用夹具测过：
  造一个 501 行的文件和一个装了 9 个 `.py` 的目录，它准确报出两条违规并 `exit 1`；
  清理后 `exit 0`。功能上没毛病。
- **我发现的问题**：我顺手做了一次字节级检查，统计每个文件里 `0x0D 0x0A` 的出现次数：
  ```
  check_limits.sh  CRLF=103   ← 全文都是 CRLF
  setup.sh         CRLF=…     ← 同样
  ```
  **编辑器在 Windows 下写出的是 CRLF**，而 AI 完全没提这件事。危险的地方在于它
  **「看起来能跑」**：`bash scripts/check_limits.sh` 这种调用方式下 Git Bash 容忍了 CRLF，
  测试全绿。但：
  - `./scripts/start.sh` 直接执行时，shebang 会被读成 `/usr/bin/env bash\r` → **bad interpreter**
  - M10 的 Docker 镜像是 Linux，**必挂**
  - 任何 CI 上都会挂

  也就是说，这个坑会一直潜伏到 M10「一条命令启动」最终验收时才炸，而那时离交付最近、
  排查成本最高。
- **我的修正**：三层防线，不靠「记得手工转换」：
  1. 新增 **`.gitattributes`**，`*.sh text eol=lf` + `pre-commit text eol=lf`，从版本库层面锁死
  2. 对已写出的 9 个文件做一次性 CRLF→LF 归一化，复检 `CRLF=0`
  3. 在 `scripts/lint.sh` 里加一步**行尾符自检**（`grep -qU $'\r'`），把它变成能自动发现的门禁
     而不是靠人记
  顺带代价：根目录文件数从 6 变成 7（`.gitattributes`），已回写 TDD §3 目录约定第 2 条
  说明原因——7 仍在 ≤8 的合规范围内。
- **结论**：**AI 不会主动考虑「产物在别的平台上还能不能跑」，尤其是它看不见字节层的
  行尾符。** 而且这类问题的恶劣之处在于**局部测试会通过**——我是在功能验证已经全绿之后
  才做的字节检查，如果只信「测试过了」就会放过去。**验证不能只验功能，还得验产物的
  物理属性**（编码、行尾、BOM、可执行位）。同一类坑我这轮已经踩到第二次：之前提交文档时
  PowerShell 的 UTF-8 输出给 commit message 加了 BOM，也是靠字节级检查才发现的。

### [M0-2] 照着文档建目录树，结果撞上了文档自己的内部矛盾

- **背景 / 我的指令**：DEV_PLAN M0 要求「建完整目录树（按 TDD §3），空目录放 `.gitkeep`」。
- **AI 给的方案**：严格按 TDD §3 的目录树逐个建目录。建完是对的——但 §3 的树里
  **根本没有 `backend/tests/`**，而 §10.1 却详详细细列了 16 个测试文件
  （`test_chunking.py`、`test_agent_with_mock_llm.py`……）。
- **我发现的问题**：把 §10.1 的清单数了一遍——**16 个测试文件 + `conftest.py` = 17 个**。
  而 FR-6-17 和 TDD §3 都规定**单目录 ≤8 个文件**。也就是说：
  - §3 漏画了 `tests/` 目录
  - 如果按最自然的写法把 17 个文件平铺进 `backend/tests/`，**超限 2 倍多**
  - 而我这次要交付的 `check_limits.sh` 正是用来卡这条线的门禁 ——
    **它上线第一天就会把项目自己的测试目录判红**

  这是两份文档各自都「看起来没问题」、合在一起才暴露的矛盾。设计阶段没人发现，
  是因为写 §10.1 的时候在列**测试内容**，写 §3 的时候在画**目录结构**，两件事分开做的。
- **我的修正**：发现 §10.1 本身已经按 **L1 纯单元 / L2 集成 / L3 端到端** 分好层了，
  直接把这个分层映射成子目录，数量刚好合规：

  | 子目录 | 对应层 | 文件数 |
  |---|---|---|
  | `tests/unit/` | L1 | **8**（正好卡上限） |
  | `tests/integration/` | L2 | 6 |
  | `tests/e2e/` | L3 | 2 |
  | `tests/`（根） | — | 1（`conftest.py`） |

  然后回写文档：TDD §3 补上 `tests/` 子树、目录约定加第 5 条说明这个冲突与解法、
  §10.1 开头加「目录约定」说明三层各落在哪。同时标注 `tests/unit/` **已达 8 的上限**，
  后续新增单元测试必须先建子目录（和 `scripts/` 的 R12 约束同理）。
- **结论**：**AI 严格执行文档的时候，最容易撞上文档自身的矛盾——而它不会停下来质疑文档。**
  它会把 §3 的树 faithfully 建出来，然后在 M1 写测试时才发现没地方放，或者更糟：
  直接平铺，让门禁在 M10 才报警。反过来看，这也是**「把约束写成可执行脚本」的价值**：
  `check_limits.sh` 一跑，文档里的隐性矛盾立刻变成显性错误。**能自动执行的约束，
  比写在文档里的约束更早暴露问题。**

### [Gate0-1] 工程门禁被自己的 uv 缓存拖死

- **目标**：在接入企业微信前，先恢复环境模板、锁定 SDK，并运行现有工程规模门禁。
- **实际现象**：本机 `uv` 不在 PATH，找到可执行文件后又因默认缓存目录权限不足失败；把
  `UV_CACHE_DIR` 指向仓库内临时目录后依赖可以正常解析。但 `check_limits.sh` 随即超过一分钟
  没有输出，看起来像 Git Bash 故障。
- **定位方式**：停止挂起进程并逐行检查脚本，发现 `find .` 虽排除了 `.venv`，却没有排除
  新增的 `.uv-cache`。脚本因此遍历 uv 下载和解包出的整个第三方源码树。
- **修正**：把 `.uv-cache/` 同时加入 `.gitignore` 与 `check_limits.sh` 的 prune 列表。修正后
  门禁约 1 秒完成，扫描 11 个项目代码文件并通过。
- **结论**：门禁脚本自身也需要性能验收。只验证“结果是否正确”不够，还要验证它能否在
  开发者真实环境中快速结束；否则 pre-commit 会变成大家绕过的摆设。

### [M1-1] Mock 数据边界必须实测才能写断言

- **现象**：验收断言需要先把 data/mock 跑一遍才有数：订单 2026-11-16~22 共 7 笔、已支付合计 121400（早期手算 122400 是错的，把 refunded 的 790 记成了已支付口径）；技术部 4 人；「张伟」在技术部与销售部重名，正好用来验证模糊搜索的歧义处理。
- **修正**：这些数据事实全部写进集成测试断言，后续改 mock 数据测试会立刻红，不会再靠记忆。
- **结论**：让 AI 生成 mock 数据很快，但「数据的边界事实」必须用脚本实测后固化，不能采信任何一方（人或 AI）的心算。

### [M1-2] pytest-socket 全局禁网与 Windows asyncio 冲突

- **背景**：pyproject 用 --disable-socket 保证测试绝不打真实网络。
- **现象**：所有 async 测试在 Windows 上 fixture 阶段就 ERROR。定位：disable_socket() 替换 socket.socket.__new__，而 asyncio 事件循环内部用 socketpair() 建自管道，被误杀。
- **修正**：含 async 的测试模块改挂 pytest.mark.allow_hosts("127.0.0.1")，pytest-socket 转而只守 connect()，本地 socketpair 放行，对外网地址禁网机制不变。HTTP 集成测试用 httpx ASGITransport 进程内直连，本就不经真实套接字。
- **结论**：全局禁网插件与目标平台的事件循环实现要做兼容性验证，白名单式放行比全局开关稳。

### [M2-1] 时间注入的文档冲突与裁决

- **背景**：TDD §7.2 主张每轮向 system prompt 注入【当前时间】以省一次工具调用；CURRENT_PLAN §2 修正 2 要求时间问题必须调 get_current_time、不再注入。
- **裁决**：按 考题 > CURRENT_PLAN > PRD > TDD 的优先级采用修正版。prompts.py 不含时间注入，并有脚本校验 SYSTEM_PROMPT 与 TDD §7.1 原文逐字一致；取舍说明已回写 TDD §7.2 状态更新。
- **结论**：文档冲突要显式裁决并回写到被覆盖的一方，不能留考古题给后来的读者。

### [M2-2] usage_or_estimate 不认 dataclass，差点丢掉真实用量

- **现象**：编排器把上游返回的 TokenUsage（dataclass）直接传给 usage_or_estimate，而它只认 dict / model_dump()，dataclass 被当成「缺失」而重新估算，真实用量被静默覆盖。
- **修正**：编排器先判 chunk.usage is not None 直接采用，只有上游确实不回 usage（Ollama / 部分网关）才走本地估算；test_agent_degrade.py 用 _NoUsageLLM 桩把两条路径分别钉死。
- **结论**：带兜底的工具函数必须写清它认识哪些输入类型，否则兜底会静默变成丢数据。

### [M2-3] query_orders 刻意不返回汇总

- 考题 Q5「上周一共多少订单」与题面「上周三的销售额」考察的正是 query_orders → calculator 两步编排。接口若顺手算好 summary，等于拿预计算冒充 Agent 能力（CURRENT_PLAN 修正 3）。工具 description 明写「不提供任何汇总数字」，集成测试断言输出里没有 summary 键，且必须出现两轮工具调用。

### [M2-4] AI 误报「工具不可用」并虚报进度

- **现象**：开发过程中 AI 执行侧多次声称 exec 工具不可用、甚至声称 M3-M6 已完成并推送；经 git log 与文件系统逐项核实均未发生，属虚报。真实存在的桥接错误原文是 Tool exec does not exists.，偶发且通常一分钟内恢复。
- **修正**：立三条规则并执行——只认工具返回原文与 exit code；每次 apply_patch 后用 git status 独立验证落地；同一命令连续失败两次先探测桥接存活再决定重试。
- **结论**：「命令失败」与「工具不可用」是两回事；没有 git / 文件证据的进度汇报一律不可信，恢复后须向用户明确更正。

### [M2-5] 换机替换后 .env 的 LLM 段被占位模板覆盖

- **现象**：.env 里 LLM_BASE_URL / LLM_MODEL 是 your-provider.example.com / your-chat-model 占位值；LLM_API_KEY 对配置默认的 MaaS 端点实测返回 401 Invalid API-key（网络本身可达，说明不是断网）；企微 BOT_ID / SECRET 仍是真实值。
- **影响**：真实模型联调（Q4-Q7 实跑）暂无法执行。Agent 层已用 MockLLM 集成测试覆盖考题行为，128 例全绿；Q10 降级路径在真实 401 与连接失败两种场景下均验证通过。
- **待办**：用户恢复真实 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL 后，运行 backend/dev_tools/agent_smoke_real.py 完成真实 Key 验证（已列入早晨操作清单）。

## M4 · RAG 管道核心（旧 DEV_PLAN 编号 M3）

### [M4-1] 阈值不能停在“短样本看起来合理”

- **背景**：设计初版把 `retrieval_min_score` 写成 0.35；短样本实测发现不相关中文余弦也有
  ~0.48，于是先把起点修正成 0.55。
- **真实语料标定**：4 份语料共索引 78 个 chunks。相关问题最低分 **0.6888**，不相关问题
  最高分 **0.5741**，建议分界中点 **0.6314**，最终配置定稿为 `min_score=0.63`。
- **第二个坑**：相对间隔初值 0.05 会把 Q1/Q3 也拒掉，因为多个相邻正确块本来就可能
  得分接近；Q3 实测 spread=0.0105，因此定稿 `min_spread=0.01`。
- **结论**：绝对阈值和相对间隔都必须用完整语料、正负样本和验收问题共同标定；不能把
  一次短句实验的数值直接当生产参数。

### [M4-2] 临时电脑有模型权重，不等于必须再装 2 GB 的 torch

- **现象**：本机已有 `D:\Models\bge-m3`，但没有 torch/sentence-transformers；直接照原脚本
  启动会失败。用户明确说明这是临时开发电脑，不希望重复下载大模型或重型运行时。
- **修正**：保留 sentence-transformers 路径，同时让 embedding 服务在其不可用时自动读取
  现有完整 ONNX 权重；backend 只增加轻量 `onnxruntime` + `tokenizers` 运行依赖。启动前设置
  `BGE_MODEL_DIR=D:\Models\bge-m3`，没有下载任何新模型。
- **验证**：真实服务返回 1024 维归一化向量，4 份语料索引和 Q1～Q3 检索均通过。
- **结论**：换机时应先盘点“权重、导出格式、运行时”三件事，缺运行时不代表缺模型；能复用
  已有 ONNX 导出时，不应为了开发验证盲目安装完整训练栈。

### [M4-3] 同名替换的回滚能力不能靠操作顺序碰运气

- **问题**：旧设计写的是“先删旧向量，再写新版本”。新文件一旦解析、embedding 或 Chroma
  写入失败，线上知识会立即消失，违反 CURRENT_PLAN 的硬约束。
- **修正**：物理向量 ID 加入 `content_hash`，新版本先完整写入；成功后原子替换
  `active_versions.json`，最后才清理旧版本。失败则只清理新版本残留，旧 active 版本继续可检索。
- **验证**：pipeline 单测钉死“写入 → 激活 → 清旧”的顺序，并覆盖写入异常时旧版本仍 active。
- **结论**：可回滚不是一句“异常捕获”，而是数据模型必须同时容纳新旧两个版本，并设置一个
  原子切换点。

### [M4-4] “异步”不等于“每个文件都 create_task”

- **初版问题**：上传接口确实能立即返回，但每个文档各自 `create_task`。管理员一次传 10 个
  文件时，会有 10 条索引链同时向 embedding 服务发批量请求；功能测试能过，限流和内存风险
  却被藏在“异步”两个字后面。
- **修正**：增加单 worker `IndexTaskQueue`，上传仍立即返回 `pending`，但解析、embedding、
  Chroma 写入按 FIFO 串行执行；停机前 `drain()` 排空队列。单测同时提交两篇文档并断言
  `max_active == 1`。
- **原文件也要版本化**：只给向量做 content-hash 版本仍不够；如果同名上传直接覆盖磁盘原文，
  新版本索引失败后虽然旧向量还能检索，引用预览却会指向新文件。最终原文件也按
  `{doc-hash}/{content-hash}/{filename}` 保存，成功切换后才删旧文件。
- **真实验收**：隔离存储下上传 `常见FAQ.md` 立即返回 pending，随后 indexed（27 chunks）；
  删除返回 27，列表归零。说明状态机、向量删除和 REST 协议在真实 BGE 服务上闭环。
- **结论**：评审异步任务不能只看“请求有没有阻塞”，还要看并发上限、停机排空和跨存储的
  一致性边界。
