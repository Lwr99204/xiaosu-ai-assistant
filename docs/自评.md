# 自评

## 我做了什么

项目是给公司做一个内部助手“小苏”。员工在企业微信里问它，它会自己决定翻文档、查考勤、查订单还是调用计算器，回答后把出处一起贴出来。我完成了后端问答、企业微信接入和 Web 管理后台。做下来感觉，难的不是把模型接上，而是让模型说的话可以被查证。

## 最得意的技术决策：让引用真的能定位原文

一开始考虑过使用 LangChain，但普通文档切分会丢失文本在原文中的位置。模型虽然能返回 `[1][2]`，系统却只能说“大概来自员工手册某一段”，无法确认它到底引用了哪些字。

所以检索链路我自己实现了一遍。每个分块除了文本，还保存 `doc_id`、标题路径、`char_start` 和 `char_end`。模型返回引用编号后，系统会检查编号是否确实对应本轮检索结果；如果引用越界，就撤回答案，而不是把无法验证的出处发给用户。后台现在可以点击引用，加载原始文档并自动滚动、高亮对应区间；测试还会验证 `chunk.text == document.content[char_start:char_end]`。

这套机制曾暴露一个真实问题：年假、报销和新人入职三题的答案明明在文档里，却被判断为“引用越界”。结合代码和真实日志排查后发现，工具输出重复携带长文本，超过 4000 字符后被截断，程序拿不到完整命中列表，合法的 `[1]` 反而找不到对应分块。

我没有为了通过验收放松引用校验，而是去掉重复数据，把片段长度从 120 提高到 600，并限制单轮最多检索两次。修复后三题全部通过：年假 13.75 秒、报销 14.07 秒、新人入职 17.54 秒。拒答阈值也用四份真实文档标定：相关样本最低 0.6888，不相关样本最高 0.5741，最终取 0.63，而不是凭感觉填写一个数字。

## 一个被迫的妥协：没有把模型输出原样逐 Token 推给用户

我原本希望企业微信里的回答生成一个字就显示一个字，但严格引用校验只有等完整答案生成后，才能确认其中的 `[n]` 能否映射到本轮真实检索结果。如果内容已经逐字发出，最后才发现引用越界，前面的假出处就无法安全收回。

因此思考过程会被单独过滤，工具执行期间只发送查询进度，完整答案生成后再统一校验引用。校验通过才整段写入正式答案，失败则替换为拒答内容。这个方案牺牲了一部分流式体验，但我选择优先保证引用可信，因为内部知识助手展示一个无法核验的出处，比回答稍慢更严重。

## 如果再给我一周

我会优先把系统从“能够演示”推进到“可以持续在公司内部使用”，而不是继续增加工具。先在真正干净的电脑上完成克隆、依赖安装、模型准备、启动和整套验收；再补企业身份认证、角色及部门级知识权限；最后整理至少二十条持续评测题，统计回答准确率、引用正确率、拒答准确率和延迟。是否引入混合检索或 Rerank，将根据评测结果决定，而不是为了增加技术名词。
