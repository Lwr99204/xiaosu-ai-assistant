## 0. 阅读说明

本文档把笔试题的 6 大功能 + 加分项，拆解成**可逐条验收**的产品需求。每条需求带三个标记：

- **来源**：对应笔试题的章节 / 评分项，便于反查扣分点
- **优先级**：`P0` 必做（不做 = 淘汰或大幅失分）｜`P1` 应做｜`P2` 加分项
- **验收标准**：可以直接动手判定通过与否的条件，不含模糊表述

需求编号规则：`FR-模块号-序号`（功能需求）、`NFR-序号`（非功能需求）。

## 1. 产品定位

「小苏」是公司内部 AI 助手。**员工侧入口是 IM（钉钉），管理员侧入口是 Web 后台。**

这个定位决定了一件容易做错的事：**Web 端聊天页只是调试/演示用的次要功能，IM 才是主战场**——题目第七章的 10 道验收题全部在 IM 里跑，只有 7.6 检查 Web 后台。所以开发顺序上 IM 集成不能压到最后。

一句话价值主张：

> 员工在钉钉里 @ 小苏，就能查公司制度、查考勤、查销售数据；答案一定带原文出处；查不到就明说，绝不编造。

### 1.1 三条产品红线（贯穿所有需求）

| 红线 | 含义 | 落地机制 |
|---|---|---|
| **不编造** | 检索不到就拒答 | 相关性阈值 + Prompt 强约束 + 无引用不输出 |
| **可追溯** | 每个答案能定位到原文段落 | 引用带 `文档名 + 章节路径 + 字符偏移`，前端可高亮 |
| **不卡死** | 任何异常都要有兜底回复 | 全链路超时 + 重试 + 降级话术，IM 侧永不静默 |

## 2. 用户角色

| 角色 | 入口 | 核心诉求 | 备注 |
|---|---|---|---|
| 普通员工 | 钉钉群 @小苏 / 私聊小苏 | 快速拿到**可信**答案，不用翻文档 | 主要用户 |
| 管理员 | Web 后台 | 维护知识库、审计对话、看 Token 成本 | 不在 Web 端聊天 |
| **面试官（验收者）** | 钉钉测试群 + Web 后台 | 跑标准清单 10 题；**现场随机改一处代码** | ⚠️ 一等公民 |

> ⚠️ **面试官必须被当成一个正式角色来设计**。题目明确说「面试时会随机挑 1-2 个让你改一处代码（比如新增一个工具、或调整 prompt）」。这意味着：新增一个工具的成本必须低到「加一个文件 + 注册一行」，改 prompt 必须不用翻代码（外置成常量/配置）。这条会直接影响 TDD 里的模块划分。

## 4. 功能需求

### 4.1 F1 文档知识库（来源：题目功能1，12 分）

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-1-01 | 支持上传 **Markdown / PDF / Word / TXT** 四种格式（题目要求 ≥3） | P0 | 各传一个文件，全部解析成功且内容可被检索到 |
| FR-1-02 | 单文件大小上限 20 MB，超限返回 413 与友好提示 | P1 | 传 25 MB 文件，得到明确错误而非 500 |
| FR-1-03 | 非法/损坏文件（如改后缀的假 PDF）解析失败，状态置 `failed` 并记录原因 | P0 | 上传假 PDF，列表显示 `failed` + 错误原因，不影响其他文档 |
| FR-1-04 | 文档列表展示：文件名、格式、大小、上传时间、**索引状态**、分块数 | P0 | 状态取值严格为 `pending` / `indexed` / `failed` |
| FR-1-05 | 删除文档后，其所有分块从向量库移除，**不再参与问答** | P0 | 删除前能命中的问题，删除后必须拒答 |
| FR-1-06 | **增量更新**：上传同名文件识别为替换，删除旧分块后重建，不产生重复 | P0（分水岭） | 同名传两次内容不同的文件，检索结果只来自新版本；分块总数不翻倍 |
| FR-1-07 | 内容去重：同名且内容 hash 完全一致时跳过重新索引 | P1 | 重复上传同一文件，`indexed_at` 不变、不重复调 embedding |
| FR-1-08 | 索引过程异步执行，上传接口立即返回，不阻塞请求 | P1 | 上传 3 MB PDF 接口响应 < 500 ms，状态先 `pending` 后转 `indexed` |
| FR-1-09 | 上传即生效：无需重启服务，索引完成后立即可被问答命中 | P0 | 对应 US-11 / 题目 7.6 |

> **关于「增量更新」为什么是分水岭**：多数人只做「插入」，导致同名文件产生两套分块，检索时新旧内容同时命中、答案自相矛盾。关键设计是 **文档唯一键 = 归一化文件名**，且 **内容 hash 用于判断是否需要重建**。

### 4.2 F2 智能问答（来源：题目功能2，18 分 — 分值最高）

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-2-01 | 基于知识库问答，答案**必须带引用** | P0 | 每条 KB 答案至少 1 个引用；无引用不输出 |
| FR-2-02 | 引用信息包含：文档名、**章节路径**（如 `员工手册 > 第三章 休假制度 > 3.1 年假`）、原文片段、字符偏移 | P0 | 满足「不只是文件名」的要求 |
| FR-2-03 | **来源定位可点击跳转/高亮**：Web 端点击引用滚动并高亮原文；IM 端展示章节路径 + 片段 | P0 | Web 端点击引用能定位到原文段落并高亮 |
| FR-2-04 | **多轮对话**：记住上下文，支持「再详细讲讲」「换种方式说」 | P0 | 题目 7.3 Q7 通过 |
| FR-2-05 | 上下文按 **会话维度隔离**，A 的对话不能被 B 接续 | P0 | 两个不同 user_id 交叉提问，上下文互不污染 |
| FR-2-06 | 上下文窗口：保留最近 N 轮（默认 10 轮 / 约 4k token），超出滚动丢弃 | P1 | 长对话不因超上下文而报错 |
| FR-2-07 | **流式输出**：边生成边返回，首字节延迟 < 2 s | P0 | Web 端可见逐字输出；不是憋完一次性返回 |
| FR-2-08 | **拒答机制**：检索不到相关内容时明确回复「文档里没找到」，不编造 | P0 | 题目 7.4 Q8/Q9 通过 |
| FR-2-09 | 拒答判定双保险：① 检索最高相关度 < 阈值直接拒答（不调 LLM）② Prompt 强约束「仅依据给定资料」 | P0 | 阈值可配置；两层都有单测覆盖 |
| FR-2-10 | 涉及敏感/隐私信息（家庭住址、身份证、薪资明细等）主动拒答 | P1 | 题目 7.4 Q8 |
| FR-2-11 | 答案语言与提问语言一致（中文问 → 中文答） | P1 | — |
| FR-2-12 | 混合意图：问题同时涉及文档与工具时，能分别处理并整合答案 | P2 | 例：「年假几天？顺便看下我上周考勤」 |

### 4.3 F3 工具调用（来源：题目功能3，12 分）

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-3-01 | 至少接入 **2 个工具**，模型**自主决定**何时调用 | P0 | 题目 7.2 Q4/Q5/Q6 通过 |
| FR-3-02 | **工具 A：内部 API（必做）** — 自建 mock 服务，提供 ≥2 个接口 | P0 | 实现 `/api/employee/{id}`、`/api/attendance`、`/api/orders` 三个 |
| FR-3-03 | **工具 B：通用工具** — 计算器 / 当前时间 / 单位换算 | P0 | 实现计算器 + 当前时间两个 |
| FR-3-04 | **知识库检索本身也注册为一个工具**，由模型决定是否查文档 | P0 | 这是「自主决策」的核心：不写死「先查库再回答」 |
| FR-3-05 | 工具调用**不得写死 if-else 关键词匹配** | P0（关键考点） | 代码评审 + 面试现场改 prompt/工具验证 |
| FR-3-06 | 工具调用轮次上限（默认 5 轮），防止死循环 | P0 | 构造互相调用的场景不会无限循环 |
| FR-3-07 | 工具入参由模型生成，需做 **Pydantic 校验**；非法入参返回结构化错误让模型自纠 | P1 | 传错日期格式时模型能重试或给出友好回复 |
| FR-3-08 | 工具执行异常/超时不冒泡成 500，转为工具级错误信息回灌给模型 | P0 | 对应「调用稳定」 |
| FR-3-09 | 每次工具调用被完整记录（工具名、入参、耗时、结果摘要），供后台日志展示 | P0 | 题目 7.6「调了哪些工具」 |
| FR-3-10 | 需要汇总计算时（如「上周一共多少订单」）能取数后自行求和 | P0 | 题目 7.2 Q5 |
| FR-3-11 | 新增一个工具的成本 ≤「1 个文件 + 1 行注册」 | P1 | 服务面试官现场改代码 |

### 4.4 F4 IM 集成（来源：题目功能4，15 分 — **核心，不接 = 直接淘汰**）

**平台选型结论：钉钉（Stream 模式）**，理由见 TDD §3.4。飞书作为第二个 adapter 列入 P2 加分。

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-4-01 | 注册为钉钉企业内部应用机器人，员工可在**群里 @小苏** 或 **私聊小苏** | P0 | 两种方式都能收到回复 |
| FR-4-02 | 采用 **Stream 长连接模式**接收消息，不依赖公网 IP / 域名 / 内网穿透 | P0 | 本地启动即可收发消息；面试官笔记本上也能跑 |
| FR-4-03 | 消息收发闭环：接收 → 调后端 → 回复，端到端 P95 < 15 s | P0 | 实测 10 道验收题 |
| FR-4-04 | **多轮对话上下文按 `平台 + 会话ID + 用户ID` 三元组隔离** | P0 | 题目 7.3 明确要求；群里 A/B 两人交叉提问互不串台 |
| FR-4-05 | 群聊场景只对 @机器人 的消息响应，不回复无关消息 | P0 | 群里发不带 @ 的消息，机器人不响应 |
| FR-4-06 | 自动剔除消息中的 @ 提及文本（如 `@小苏 `），避免污染 query | P1 | 提问内容干净 |
| FR-4-07 | **引用来源在 IM 里清晰呈现**：Markdown 消息展示「文档名 › 章节路径 + 原文片段」 | P0 | 满足「卡片/Markdown/链接均可」 |
| FR-4-08 | **错误兜底**：后端崩溃 / 模型超时 / Key 无效时，IM 侧必须收到友好提示 | P0（淘汰相关） | 题目 7.5 Q10：改成无效 Key，IM 收到提示而非永久无响应 |
| FR-4-09 | 兜底必须有**硬超时**：超过 N 秒（默认 60）主动发送超时提示，不允许静默 | P0 | 断网/挂起场景下用户仍有反馈 |
| FR-4-10 | IM 侧长任务先发「正在思考…」占位，完成后**追加一条**正式答案消息。钉钉普通 Markdown 消息**不支持编辑已发送内容**，因此 P0 实现为「占位 + 追加」两条消息；单条卡片内流式刷新属 P2（见 FR-4-14） | P1 | 避免用户以为掉线 |
| FR-4-11 | 消息去重：同一 `messageId` 重复推送只处理一次 | P1 | 钉钉重试场景不产生重复回答 |
| FR-4-12 | IM adapter 抽象化：新增一个平台只需实现统一接口，**业务逻辑零改动** | P1 | 支撑加分项「逻辑能复用」 |
| FR-4-13 | 接入第二个平台（飞书长连接模式） | P2（加分） | 同一套 agent/rag 代码跑通两个平台 |
| FR-4-14 | 富消息：钉钉 AI 卡片流式输出（打字机效果） | P2（加分） | IM 里也能看到逐字输出 |
| FR-4-15 | 管理员在后台可查看 IM 连接状态（已连接/断开/最后心跳时间） | P1 | 对应 FR-5-06 |

> ⚠️ **排期警告**：这一项需要**人工注册钉钉开发者账号、创建应用、拿 AppKey/AppSecret、建测试群**，是唯一无法纯靠写代码完成的环节，且面试要现场演示。**必须在开发早期就并行推进**，不能留到最后。
